# The Linux deployment contract — how deepskopion software reaches a board

**Deployment Contract.** This is the one place that answers *"how does the capture
daemon start on the board?"*. If something else in the repo answers it
differently, that thing is wrong, and
`sw/linux/deployment_contract.py` is
supposed to have failed the build before you read it.

The machine-readable source of truth is
`sw/linux/deployment_contract.yml`. The
section below is **generated from it**, so the prose and the declaration cannot
drift apart in silence.

## The short answer

`/init` from the overlay is PID 1, it runs `/etc/init.d/S*` in order, and
`S99deepskopion-stream` — last in that order — launches
`python3 -m sw.stream`. There is no systemd anywhere in this product. Read the
daemon's output with:

```sh
tail -f /var/log/deepskopion-stream.log     # the daemon's output
cat /proc/cmdline                           # ds_source= decides --source
```

**Init system: `busybox`. There is exactly one, on every target that boots Linux (de25_datalogger, pfsoc_datalogger, zybo_datalogger).**

PID 1 is `sw/linux/rootfs_overlay/init`, from the overlay. /init mounts proc/sys/dev, then iterates /etc/init.d/S* in lexical order and calls `<script> start` on each executable one (busybox-traditional rcS), then execs an interactive shell.

| file in the overlay | tracked / staged | what it starts | why it is where it is |
|---|---|---|---|
| `init` | tracked | PID 1 itself — the /etc/init.d/S* chain, then an interactive shell | Overrides the stock /init from `rr linux rootfs`. |
| `etc/init.d/S01hostname` | tracked | nothing — sets the kernel hostname from /etc/hostname | First, so every later script and the login shell see the right name. |
| `etc/init.d/S40network` | tracked | eth0, using DHCP or owner-supplied `ds_ip=`/network.conf state | Before dropbear and before the daemon: both bind sockets. The public image contains no fallback address. |
| `etc/init.d/S49dropbear` | tracked | the dropbear sshd on :22 (its binary is a per-arch staged artefact: armhf for the Zynq targets from sw/linux/stage_dropbear_overlay.sh, riscv64 for the PolarFire kit from its own python_overlay) | After the network, before the daemon. Host keys generate on first use; SSH remains closed until the owner provisions an authorized key. The DE25 image leaves this script and deepskopion-authorize-key out: it stages no AArch64 dropbear, so it has no SSH server (tools/de25_linux_image.py DE25_OVERLAY_EXCLUDE). |
| `etc/init.d/S99deepskopion-stream` | tracked | THE CAPTURE DAEMON — `python3 -m sw.stream`, listening on 0.0.0.0:7475 | Last (S99), so the network is up and the datalogger defaults are armed before the ring is drained. This is the answer to "how does the capture daemon start on the board?". |

The daemon's source is **`sw/stream/`** — the only on-disk truth. `sw/linux/stage_daemon.sh` rsyncs it into `sw/linux/rootfs_overlay/usr/local/share/deepskopion/sw/stream/` at `rr linux rootfs` time; that copy is **generated**, so it is gitignored and a fresh clone does not have it.

- `--source` comes from kernel cmdline `ds_source=` from targets/<name>.yml linux.bootargs.
- Listens on `0.0.0.0:7475 (wave_stream_v1) + 0.0.0.0:7476 (wave_events_v1)`; log at `/var/log/deepskopion-stream.log`; pidfile `/var/run/deepskopion-stream.pid`.

Other **staged artefacts** in the overlay — gitignored, regenerated by their script, never edited in place:

- `sw/linux/rootfs_overlay/usr/sbin/dropbear` ← `sw/linux/stage_dropbear_overlay.sh`
- `sw/linux/rootfs_overlay/usr/bin/{cansend,candump,cangen,candatalogger}` ← `sw/linux/stage_can_overlay.sh`
- `sw/linux/rootfs_overlay/usr/bin/scp` ← `sw/linux/stage_openssh_scp_overlay.sh`
- `sw/linux/pfsoc/python_overlay/usr/sbin/dropbear` ← `sw/linux/pfsoc/build_python_overlay.sh`

**Owner-supplied private files** — placed by the image owner for a private build, gitignored by their exact path, never committed, never in a public image:

- `etc/deepskopion/authorized_keys` (read by `etc/init.d/S49dropbear`) — The owner's SSH public key for a private image build. S49dropbear copies it to /root/.ssh/authorized_keys on boot and starts dropbear; without it SSH stays closed. Public images never carry it.

**Not autostarted** (stated so "there is no unit for it" is an answer, not a gap):

- `sw/telemetry` — not staged into the rootfs at all; copied to the board and run by hand (ssh with cat on the Zybo Z7-20 and the PolarFire SoC Discovery Kit; on the DE25, which has no SSH server, onto its card's root partition), see docs/software/telemetry_exporter.md. Its exporter is a periodic snapshot tool, not part of the capture path. It carried a systemd service+timer recipe until SW-C0; on a busybox initramfs that recipe cannot run.
- `sw/linux/rootfs_overlay/usr/local/bin/deepskopion-self-test` — on-board self-test, invoked manually from a shell. Deliberately not wired into the rcS chain — a self-test that runs on every boot competes with the daemon for the ring it is testing.

**Mechanisms this repo does not use:**

- **systemd** — No image this repo builds contains systemd. A unit in the overlay is dead weight that reads as authoritative.
- **petalinux** — Forbidden by house rule, and it is the ONLY justification the systemd variant ever had. Python reaches the rootfs through a per-arch python_overlay (armhf Zynq built by sw/linux/build_buildroot.sh and sw/linux/extract_python_overlay.sh; riscv64 PolarFire built by sw/linux/pfsoc/build_python_overlay.sh), not through a PetaLinux profile.

Telling source from artefact, for any file under the overlay: tracked by git = source, you may edit it; matched by .gitignore = staged artefact, regenerate it and never edit it; neither = a mistake.

### Bench targets and tool images

The targets above are the shipped products. Bench targets declare their boot
behaviour in a contract sidecar beside them, which the checker reads with the
same rules. Neither the bench targets nor their sidecar are part of this
distribution.

Some bench images are tools, not product images: they boot with their own
PID 1 from their own overlay and start nothing else (no `/etc/init.d/S*`
chain, no `inittab`). They are listed under `tool_images` in that sidecar,
each with its target, overlay, PID 1 file
and `autostart: none`. A target that builds a Linux rootfs is declared in
`boot.targets` (or a sidecar's `targets`) or in `tool_images`, never both and
never neither. Tool images are not in any release or supported-target list.

## Why this document exists

Three descriptions of the deployment model were live at once, and they
disagreed:

- `sw/linux/rootfs_overlay/etc/init.d/S99deepskopion-stream` — tracked, real,
  and shipping;
- `docs/software/systemd-examples/*.service` — two units presented as
  "examples", with no statement of what would ever consume them;
- earlier design notes that suggested *both* an init script and
  `etc/systemd/system/deepskopion-stream.service` were staged in the overlay.

An agent or an engineer reading the tree found an init script in one place and
"examples" in another, with nothing saying which was authoritative — so every
bring-up re-derived the answer, and some derivations got it wrong. The cost was
not theoretical. In earlier revisions the units really were in the overlay, so
`rr linux rootfs` copied one into every image built — into a rootfs that has no
systemd in it. Measured 2026-08-02 by unpacking the initramfs out of a deployed
`uImage`:

```
sbin/init -> ../bin/busybox      # busybox, not systemd
usr/lib/systemd                  # does not exist
```

That made `journalctl -u deepskopion-stream` the documented way to check the
daemon: a command that cannot work on any image this repo builds, handed to
people trying to find out whether the daemon was running.

## The systemd variant is dropped, and why (the PetaLinux question)

Earlier notes justified the systemd variant with *"PetaLinux/systemd profiles"*.
PetaLinux is a **hard rule NO** in this house — never `petalinux-build`, never
`bitbake`, never raw `dtc`. So the only stated reason for the second mechanism
was a flow we do not run, which leaves the variant with no justification at
all rather than a weak one.

**There is one autostart mechanism, busybox init.** The `.service` files are deleted, not relabelled, for three
reasons:

1. No target builds a systemd rootfs, and none is currently planned. A mechanism with no target that builds it cannot be tested, so
   it can only rot.
2. Python gets into the rootfs through a **per-arch python overlay**, built
   from upstream Buildroot: the armhf Zynq overlay by
   `sw/linux/build_buildroot.sh` and `sw/linux/extract_python_overlay.sh`. That
   need is already met by a flow the house rules permit.
3. The units carried their own `--source ddr` / `--source eye`. Which source a
   board runs is already decided, once, by `ds_source=` on the kernel cmdline
   precisely because a per-image copy of that decision cannot
   survive a reboot on a tmpfs rootfs. A second, silently divergent owner of
   that choice is a defect waiting for a reader who trusts it.

**If a systemd target becomes real** — a future target may land an image that is not
busybox — the answer is not to keep a speculative unit in the tree today. It is
one commit that does all of: declare the mechanism in
`sw/linux/deployment_contract.yml`, stage the unit in the overlay, extend the
check, and reconcile the unit's `--source` with `ds_source=` so the selection
still has exactly one owner.

## What is checked, and how to see it fail

`python3 sw/linux/deployment_contract.py` fails, naming the file, when:

| the repo does this | the check says |
|---|---|
| an autostart-shaped file appears in the overlay that the declaration does not list | it "starts something at boot but is NOT declared" |
| a declared autostart file is missing from the overlay | "the contract promises a boot step no image performs" |
| the generated section above drifts from the YAML | "the document and the overlay would tell a reader different things" |
| a new target builds a Linux rootfs without being declared | "a board whose boot behaviour the deployment contract does not describe" |
| a file under the overlay is neither tracked nor gitignored | source and staged artefact are no longer distinguishable |
| `etc/systemd/`, `usr/lib/systemd/` or `etc/xdg/autostart/` appears in the overlay | that mechanism "is not used by any image this repo builds" |
| a bound doc puts `journalctl`, `systemctl`, `petalinux-*` or `bitbake` in a **fenced code block** | "a reader who runs it gets nothing" |

The last one is deliberately scoped to copyable commands: prose may discuss
systemd (this page does), but a command a reader can paste may not come from a
flow that does not exist here.

The check is not something to remember to run. `sw/linux/stage_daemon.sh` runs
it first, and every Linux target declares that script as its
`linux.rootfs.stage_command`, so `rr linux rootfs` **aborts** rather than baking
an image whose boot behaviour disagrees with this page.
`sw/linux/tests/test_deployment_contract.py` proves each failure above by
constructing it, rather than asserting that it would be caught.
