# Contributing to Deepskopion

Deepskopion is an open hardware and software reference design for embedded multi-protocol datalogging. We welcome contributions from the community, including new board ports, additional protocol dataloggers, decoder enhancements, and bug fixes.

---

## 1. Developer Certificate of Origin (DCO)

Contributions are accepted under the **Developer Certificate of Origin (DCO) Version 1.1**, matching the licensing model stated in [`LICENSE.md`](LICENSE.md). **No Contributor License Agreement (CLA) is required.**

By submitting a pull request or patch, you certify that you have the right to submit the work under the project's open licenses:
* **CERN-OHL-W-2.0** for gateware, RTL, testbenches, and hardware design documentation.
* **MPL-2.0** for software (capture daemon, protocol decoders, telemetry, tooling, wire contract).

### Sign-off Requirement

Every commit of an outside contribution must include a `Signed-off-by:` line in the commit message (DCO). Maintainer commits, including those made with automated tools, are exempt: a sign-off is a personal certification, and a tool does not make it in a person's name.

```
Signed-off-by: Random J Developer <developer@example.org>
```

You can add this automatically using Git:
```bash
git commit -s -m "feat(i2c): add 10-bit addressing support"
```

## 2. Hardware-Validated PR Acceptance Rule

Deepskopion bridges FPGA gateware and embedded Linux software. Software simulations and unit tests are necessary but insufficient to guarantee correct operation on real silicon.

Therefore, pull requests modifying RTL sources, capture daemons, kernel device tree bindings, or target definitions are **accepted only when validated on physical hardware**:

1. **Name the Target Board**: Explicitly state which physical board was used for validation (e.g. Digilent Zybo Z7-20, Terasic DE25 Agilex-5, or a newly submitted board target).
2. **Attach Hardware Run Evidence**: Include the execution log and artifact (`run.json`) generated by running the hardware validation contract:
   ```bash
   rr hw run <REQ_ID> --probe <xsdb|juart> --write
   ```
   The default probe is an in-memory mock and proves nothing about a board.
3. **Pass Simulation Regressions**: The entire simulation suite must pass cleanly without regressions. Stage the locked packages first: a fresh clone carries no `libs/open-logic/` or `libs/enclustra/`, and without them the suite fails on missing sources rather than on your change.
   ```bash
   rr workspace sync
   rr sim run
   RR_QUEUE_SIMS=1 python3 -m pytest tools/tests/
   ```

Pull requests submitted without physical hardware execution evidence will not be merged.

## 3. Project Roadmap and Priorities

We actively seek contributions in two primary areas:

### Additional FPGA SoC Board Ports
Deepskopion is designed to be portable across FPGA vendors and SoC platforms. Supported today: Digilent Zybo Z7-20, Terasic DE25 and the Microchip PolarFire SoC Discovery Kit. We invite board targets for development platforms that engineers frequently use:
* Efinix Ti60 with the Sapphire RISC-V SoC
* AMD/Xilinx Zynq UltraScale+ MPSoC boards (e.g. Ultra96-V2, ZCU102/104, Kria KV260/KR260)
* Further Microchip PolarFire SoC boards (e.g. Icicle Kit)
* Intel Cyclone V SoC and MAX 10 platforms
* Open FPGA toolchain boards (e.g. ECP5 / Gowin with soft-core SoC or external host)

### New Protocol Dataloggers
The datalogger aggregation architecture is modular. We are expanding the suite of hardware dataloggers, with **EtherCAT** as the first priority:
1. **EtherCAT**: Industrial Ethernet datalogger with cycle-accurate frame capture, datagram header parsing, and sub-microsecond time-alignment.
2. **SPI Variants**: Standard SPI (2-wire, 3-wire, 4-wire) alongside existing QSPI flash logging.
3. **Automotive & Industrial Buses**: LIN, SENT (SAE J2716), Modbus RTU / RS-485.
4. **Custom Protocols**: Interfaces for proprietary or domain-specific bus protocols.

To propose a new protocol, open an issue using the [new protocol proposal template](.github/ISSUE_TEMPLATE/new_protocol_proposal.md).

## 4. Development Workflow

### Tooling Prerequisites
* **RouteRTL SDK**: `pip install routertl` (minimum version floor: `5.7.0`)
* **Vendor EDA Toolchains**:
  * AMD Vivado 2024.1 (Standard or Enterprise) for Xilinx targets
  * Intel Quartus Prime Pro 25.3 for Agilex-5 targets
* **VHDL Simulator**: NVC (minimum version floor: `1.19.3`)
* **Python**: Python 3.11 to 3.14

### Working with Targets
Targets define the hardware platform, datalogger instance mix, pin mapping, and tool options:
```bash
# List available targets
rr target list

# Select a target
rr target set zybo_datalogger    # Digilent Zybo Z7-20 CAN-free default
rr target set de25_datalogger    # Terasic DE25 Agilex-5 default
rr target set pfsoc_datalogger   # Microchip PolarFire SoC Discovery Kit

# Materialize the packages the target's committed lock names, and build
rr pkg install
rr synth run
rr program run
```

## 5. Testing and Regression Guards

A test suite that only passes is not proof of verification power. Every new test or bug fix must demonstrate **power**:

* **Baseline**: Demonstrate that the test fails against the code prior to the fix.
* **Mutation**: Demonstrate that intentionally breaking or deleting the guarded mechanism causes the test to fail.
* **Caller-Reachable Surface**: Assert against CLI exit codes, rendered outputs, wire streams, or hardware registers, rather than private helper return values.

---

## 6. Code Style and Conventions

* **VHDL**: VHDL-2008 standard. Follow clean synthesis and simulation practices. Maintain synchronous resets and documented clock-domain crossings.
* **Python**: Python 3.10+ typed syntax. Clean formatting, no trailing whitespace, and minimal external dependencies on on-board daemon code.
* **License Headers**: All new hardware/doc files fall under CERN-OHL-W-2.0, and software files fall under MPL-2.0 as declared in [`REUSE.toml`](REUSE.toml).
